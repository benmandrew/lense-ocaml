# An OCaml layout printer: design note

lense prints the memory layout of C and C++ records from clang's own layout engine. An OCaml version has to show something different. In C++ the questions are about bytes: *padding*, alignment, virtual table pointers and base placement. OCaml has a *uniform representation*, so those questions mostly disappear. The interesting part is how each type maps onto immediates, blocks and tags.

## The runtime model

Every OCaml value is one machine word. An *immediate* has its low bit set and carries a 63-bit integer on 64-bit targets. Anything else is a pointer to a *block* on the heap. Each block starts with a header word holding three fields: the size in words (*wosize*), two bits of garbage collector (GC) colour, and an 8-bit *tag*. The tag says how the GC and the runtime read the fields that follow. Sizes in this note and in the tool's output leave out the header word, which is the count `Obj.size` reports.

So a record of five fields is a header plus five words, whatever the field types are. A byte map in the style of lense would show the same picture for every record. The tool earns its place by answering other questions. Which constructors become immediates? Which tag does each block get? When does the compiler drop the block altogether?

## What the tool shows

**Variants.** Constant constructors become immediates numbered 0, 1, 2… in declaration order. Non-constant constructors become blocks with tags 0, 1, 2…, counted separately. In `type t = A | B of int | C | D of string`, `A` is immediate 0, `C` is immediate 1, `B` is a block with tag 0 and `D` is a block with tag 1. The two counters are independent, and readers often expect one shared counter. OCaml 5.5 accepts at most 244 non-constant constructors per type, with tags 0 to 243. OCaml 5 added `Forcing_tag` at 244 and `Cont_tag` at 245, below `Lazy_tag` at 246, so the tags from 244 up belong to the runtime.

**GADTs.** A *generalised algebraic data type* (GADT) uses the same representation as an ordinary variant. Type indices and type equalities are erased at compile time, and *existential* fields are plain uniform values. The tool numbers GADT constructors as an ordinary variant and marks each existential field, so constructors that the type checker keeps apart can be seen to share a runtime shape.

**Records.** A record is a block with tag 0 and its fields in declaration order. There are three special cases. A record whose fields are all `float` is stored flat, with unboxed doubles and `Double_array_tag` (254). A record or single-constructor type marked `[@@unboxed]` has no block at all. An *inline record* (`C of { x : int; y : float }`) puts its fields directly in the constructor's block, with the constructor's tag. Inline records never get the flat-float case, so `y` stays a pointer to a boxed float.

**Polymorphic variants.** A constant polymorphic variant is the immediate hash of its label. A non-constant one is a two-field block `[hash; argument]`, and a multi-argument payload becomes one pointer to a tuple. Two labels can hash to the same value, and the compiler rejects that. The tool reports collisions across every file it is given.

**Exceptions and extensible variants.** A constant extension constructor is its own *slot*: a block with `Object_tag` (248) holding the name and a unique identifier. A non-constant one is a tag-0 block whose first field points to that slot, followed by the arguments.

**Modules.** At runtime a structure is a block holding its value-bearing items in order: values, submodules, exceptions and classes. Types and module types take no slot. A functor is a closure. A submodule is a pointer to a tag-0 block. A named structure, including the compilation unit itself, is one block for the whole program, so it says nothing about per-instance memory, and the tool does not show it. Declarations inside submodules are still listed under qualified names such as `Inner.point`. A first-class module is a value that can be stored per instance, so the tool shows it. Packing `(module M : S)` *coerces* `M` to `S`: unless `M` already has the items of `S` in the same order, it copies them into a new block in the order of `S`. Every value of type `(module S)` is therefore a tag-0 block whose layout depends on `S` alone, whatever `M` looked like. The tool prints `(module S)` with that block once per module type, in source order with the types: at the declaration of `S` when that is in the file, otherwise at its first use. `--type S` filters it. Constraints such as `with type t = int` add no field, and a package type whose module type is a functor type is not shown.

**Closures, objects and lazy values.** Closures use `Closure_tag` (247), with a code pointer, a *closinfo* word (arity and the start of the environment) and then the environment. A value of function type points to such a block, except for the second and later functions of a `let rec ... and ...` set. Each of those is an `Infix_tag` (249) pointer into the block of the set, on `ocamlopt` and `ocamlc` alike, so the type does not fix the tag and the tool predicts a closure with either tag. Objects use `Object_tag` with a method table. Lazy values use `Lazy_tag` and `Forward_tag`. Each one belongs to a line of code, so the report lists them in source order with the types and starts each with its line. Flambda changes closure shapes, so a closure's layout depends on the compiler configuration as well as the code. The report names that configuration once, at the top.

## Where the information comes from

The compiler's own libraries, `compiler-libs`, play the role of clang LibTooling. The tool can type-check source directly or read `.cmt` and `.cmti` files produced with `-bin-annot`. From the typed declarations it reads `record_representation` (regular, float, unboxed, inlined or extension) and the constructor tags that `Datarepr` assigns. For first-class modules it reads the items of the module type in the package type. A `.cmt` names its source file, and the tool reads that source only when it matches the digest that the `.cmt` records. OCaml 5.5 records a BLAKE128 digest and OxCaml a Message Digest 5 (MD5) digest, so the tool checks each with its compiler's own hash. Without the source, types print in the compiler's order instead of as written. A `.cmt` also keeps only summaries of its environments, so before the tool reads closures from it, it rebuilds every environment in the typed tree through `Analyze.rebuild_env`. This follows the existing lense rule of reading layouts from the compiler's data structures instead of parsing its debug output.

| lense (C++) | OCaml equivalent |
|---|---|
| clang LibTooling, `ASTRecordLayout` | `compiler-libs`: `Types.type_declaration`, `record_representation`, `Datarepr` constructor tags, module type items |
| Pinned to LLVM 23 | Pinned to OCaml 5.5, because `compiler-libs` changes between releases |
| Cross-check with `-fdump-record-layouts` | Cross-check with `-dlambda`, which prints `makeblock <tag>` and constant numbering |
| Fuzz oracle: clang 23 | Runtime introspection with `Obj.is_int`, `Obj.tag` and `Obj.size` |
| Emscripten build of clang for the web | `js_of_ocaml` or `wasm_of_ocaml` compiling `compiler-libs` |

The fuzz oracle is simpler than in the C++ version. A generator writes random type declarations and constructs values of them. The test program then inspects each value with the `Obj` module and compares the result with the tool's prediction. It is compiled with both `ocamlopt` and `ocamlc`, so each prediction is checked on both backends. The ground truth comes from the running program, so no second compiler is needed.

The web front end in `web/` is also simpler. The [OCaml playground](https://ocaml.org/play) already runs the compiler in the browser through `js_of_ocaml`. The front end takes the same route, which avoids the custom WebAssembly build of clang that lense needs.

## OxCaml

Jane Street's OxCaml branch adds *unboxed layouts* such as `float#` and `int32#`, and *mixed blocks* that store flat, unscanned fields after the scanned ones. Mixed blocks have real byte-level layout. With them, a byte map of the lense kind becomes useful again. An abstract type marked `[@@immediate64]`, or declared as `type t : immediate64`, is an immediate on any 64-bit target, bytecode included. OxCaml counts such a type as ignorable by the GC only when it compiles native code, so the tool checks the type's bound itself when the word size is 64, and shows the type as immediate.

## Stage 0 results

The tag numbers and representation rules in this note were first written from memory. Stage 0 checked each one on OCaml 5.5.0 and 5.5.1, by inspecting real values with the `Obj` module and reading the compiler's `-dlambda` output. `test/stage0.t` repeats both checks on every `dune test`, so a compiler change that breaks a rule fails the tests.

**Confirmed.** Constant and non-constant constructors use separate counters, and GADTs use the ordinary numbering. All-float records are `Double_array_tag` (254) blocks, whether their fields are mutable or not. Records and constructors marked `[@@unboxed]` have no block. Inline records take the constructor's tag and never get the flat-float case, even when every field is a `float`. A constant polymorphic variant is the immediate hash of its label. A non-constant one is a block `[hash; argument]` of size 2, and a multi-argument payload is one pointer to a tuple. A constant exception is an `Object_tag` (248) block of size 2, holding its name as a string and an immediate identifier. A non-constant exception is a tag-0 block whose field 0 is that slot. A structure is a tag-0 block of its value-bearing items in order. Closures use `Closure_tag` (247), and lazy values use `Lazy_tag` (246) before they are forced.

**Wrong.** The note said a type could have 246 non-constant constructors, because tag 246 is `Lazy_tag`. OCaml 5.5 accepts at most 244, with tags 0 to 243. A type with 245 fails with "Too many non-constant constructors -- maximum is 244 non-constant constructors". OCaml 5 added `Forcing_tag` at 244 (a lazy value being forced) and `Cont_tag` at 245 (an effect continuation), and the note did not account for either.

**Not in the note.** Building the tool found six more rules. An empty float array `[||]` is a shared tag-0 *atom*, so a `float array` field has tag 254 only when the array is not empty. A lazy value built from a constant, or already forced, can be the value itself, so a `Lazy.t` field can be an immediate. A class in a structure, and so in a package layout, takes one field, a tag-0 block of size 3 on OCaml 5.5 and of size 4 on OxCaml. An `external` takes no field in its structure. The last two concern the tooling. Record field types in `compiler-libs` are wrapped in `Tpoly` nodes. Dune's `BUILD_PATH_PREFIX_MAP` rewrites the build directory that a `.cmt` file records, so the tool looks for that directory among the `.cmt` file's ancestors.

## Stage 3 results

One OCaml 5.5 build reads both compilers. `vendor/oxcaml` holds the *frontend* of OxCaml 5.2.0+ox (parser, type checker and Lambda) as the wrapped dune library `oxfront`, which OCaml 5.5 compiles. The sources in `src/core` are built twice. `src/core55` builds `lense_core_55` against compiler-libs, and its dune rule copies `compat_55.ml` to `compat.ml`. `src/coreox` builds `lense_core_ox` with `-open Oxfront`, and its rule copies `compat_ox.ml`. Both libraries link into one executable, and `--compiler 5.5|ox` picks one, by default from the magic number of a compiled input. The 74 OxCaml standard library `.cmi` files are compiled from the vendored sources by `oxc.bc.exe`, OxCaml's `ocamlc` driver built by OCaml 5.5 as bytecode, so the web build does not wait for a native build of `oxfront`. The mixed-block code is only in `compat_ox.ml`. `test/ox/mixed.t` holds the OxCaml goldens and runs in plain `dune test`. OxCaml output matched the earlier build on the 5.2.0+ox switch on 424 of 424 inputs, and 5.5 output matched on 420 of 420. The field order of a mixed block comes from the compiler's own `Mixed_block_shape` module (`lambda/mixed_block_shape.ml`, part of the vendored frontend), and the tool does not derive it again.

**Native code.** Values come first, then flat fields, each group in declaration order. Each flat scalar takes a whole word, even `int8#`, `int16#`, `int32#` and `float32#`; the compiler's comment says they "aren't packed tightly". An `int32#` is written with a 32-bit store, an `int16#` with a 16-bit store and an `int8#` with an 8-bit store, so the rest of the word is unused. A `vec128` takes two words. The header records the length of the scanned prefix, and `Obj.Uniform_or_mixed` reads it back. Unboxed products (unboxed records `#{...}` and unboxed tuples `#(...)`) inside a block are split. Their value parts join the scanned prefix and their flat parts join the flat suffix, and an unboxed record type has no block of its own. A single-field unboxed record has the layout of its field, so the compiler's `Mixed_block_shape` paths pass it by and its field takes its place. In `{ m : #{ sa : #(float# * string) } }` the string slot is `m.sa.1`, a pointer, and a field of type `#{ sv : string }` is a pointer to a string. A record of only `float` and `float#` fields is stored entirely flat, and its `float` fields are boxed again when read. A record of only `float#` fields is a `Double_array_tag` block, like an all-`float` record. Extension constructors and exceptions cannot have unboxed fields, because the compiler rejects them.

**Bytecode.** The compiler's own runtime header calls these *faux mixed blocks*. Bytecode keeps declaration order, with one scanned field per declared field. Flat fields are boxed: `float#` as a `Double_tag` block, `int32#`, `int64#` and `nativeint#` as custom blocks, `int8#`, `int16#` and `int#` as immediates, and unboxed products as tag-0 blocks. The block sizes differ between the backends whenever products are present. The fuzz oracle generates mixed records and constructors on OxCaml, with scalar flat fields of eight kinds, unboxed tuples and all-float records. It checks native code through `Obj.raw_field` bits and the scanned prefix length, and bytecode through the boxed values. A planted bug that reversed the slot order gave 7 mismatches in 6 rounds. The fuzz executable is built by OCaml 5.5 and checks OxCaml when the `ocamlfind` on `PATH` is OxCaml's. Runs of 200 rounds from `_build/default/test/fuzz/fuzz.exe` with the OxCaml switch first on `PATH`, at seeds 1000 and 5000, each made about 17,300 checks per backend, with 0 failures.

**One build.** The frontend is a wrapped library, so its modules become `Oxfront.Types`, `Oxfront.Typedtree` and so on, and do not clash with the compiler-libs modules of the same names. Its `config.ml` is built from OxCaml's boot configuration plus `vendor/oxcaml/config.overrides`. The overrides must set `runtime5 = true`, or the frontend rejects mixed records. They also name an arm64 macOS target in the architecture, system and host strings, which changes `Config` values and no representation. `parser.ml` is generated once and checked in, because dune's `menhir --infer` prints `Oxfront.X` paths inside a wrapped library. `misc.ml` needs one patch, for the `out_width` field that OCaml 5.5 added to `Format`. The vendored tree is 16 MB, of which `parser.ml` is 6.3 MB. A clean build takes 18 s instead of 0.9 s, and the native binary is 26.0 MB instead of 11.8 MB. The release web script is 6.1 MB (1.68 MB gzipped) instead of 2.0 MB (0.67 MB), and the OxCaml standard library `.cmi` files add 1.5 MB. Each OxCaml upgrade means regenerating the vendored tree with `scripts/vendor-oxcaml.sh OXCAML_SRC`.

## Stage 4 results

The report shows the closures, lazy values and objects that a unit allocates, unless `--no-values` is given. They add 10 ms to a 700-line file on the command line, and 103 ms on the page (78 ms to 181 ms). The code is in `src/core/values.ml`, and the parts that differ between backends are in `compat_55.ml` and `compat_ox.ml`. Closures are read from the *Lambda* code that each backend compiles. Only closures made inside a function body are shown. A closure outside every function, such as a top-level function or a closure in a module, is made once when the unit initialises, so it costs nothing per value. Functor bodies count as function bodies, because each application makes new closures. The tool builds it as the compiler drivers do, with `Translmod.transl_store_implementation` for native code and `transl_implementation` for bytecode, followed by `Simplif`. Lazy values follow `Typeopt.classify_lazy_argument`. Objects follow the slot order that `Translclass` allocates, because no compiler data records it. `--backend` picks whose closures to print: native code by default, bytecode, or both. With both, each closure appears once. Its two blocks pair up by the name and binding of their first function. When the two layouts differ, the report shows each under its backend's name. The page has the same choice. An interface allocates nothing, so the page turns these controls off for an `.mli`.

**Native code.** Without flambda, native code uses the `Closure` middle end. Each function in a set takes 2 words at arity 1, a code pointer and the closinfo word. At any other arity it takes 3 words: a code pointer for partial application or tuple splitting, the closinfo word, and the code pointer of the full function. Every function after the first has an `Infix_tag` (249) header word before it. The captured variables follow, in `Ident` order. Top-level values of the unit are not captured, because native code reads them from the module block. Closure compiles a block whose environment it does not need as a constant, one for the whole program. That covers a function with no free variables, and also one whose free variables Closure replaces, such as a known constant or a closed function it calls directly. The tool runs `Closure.intro` as `ocamlopt` does and keeps only the functions of a `Uclosure` with an environment. Cmmgen makes a `Uclosure` without one a constant. Without a `.cmx` for a module the code uses, as on the page, Closure knows less about that module's values. It can then report a block that `ocamlopt` would make a constant. The fuzz oracle calls each closure maker twice: two calls give the same block exactly when the tool shows no closure in native code. `Simplif.split_default_wrapper` splits a function with defaulted optional arguments into a wrapper and an inner function that share one block, so `opt ?(x=1) y` is a block of size 7 for 2 functions.

**Bytecode.** Each function takes 2 words, and the arity in its closinfo word is 0. A function captures the top-level values it uses, and there is no default-argument split. `Simplif` skips some `let` optimisations under `-g`, so the prediction is for `ocamlc` without `-g`. On both backends the closinfo word holds the arity in its top 8 bits, then the start-of-environment field, then a low tag bit of 1. OxCaml takes one bit of the start-of-environment field for a flag, which leaves it 54 bits instead of 55. Flambda 2, the OxCaml native middle end, reverses function sets, propagates constants and reorders the environment. The tool therefore reports native closures on OxCaml as not predicted, and predicts bytecode closures on OxCaml as usual.

**Lazy values.** A constant, a function or a plain identifier gives the value itself. A float that cannot be short-cut, or an identifier whose type might be a float or a lazy value, gives a `Forward_tag` (250) block of size 1. Anything else gives a `Lazy_tag` (246) block holding a closure, and forcing it turns the block into a `Forward_tag` block.

**Objects.** An object is an `Object_tag` (248) block whose field 0 is the method table and field 1 the object id. Each class level allocates new slots in a fixed order. First comes one slot for each class parameter or class-level `let` that a method uses. Then come the level's own vals that are not overrides, in declaration order, and then the slots of each inherited class in turn. A name that already has a slot keeps it. An unused parameter takes no slot, because `Simplif` drops its `StrictOpt` let. A class or object inside an expression (under `Translobj.oo_wrap`) can get an extra slot right after the object id. It gets one when its methods or its `initializer` clauses use variables bound in the enclosing top-level item, because `Translclass` compiles initializer code with the same substitution as methods. The slot holds a tag-0 block of those variables. `self` is bound inside the object and is not a variable of the enclosing item, so a method that calls `self#m` gives the object no slot. Top-level classes have no such slot.

The fuzz oracle builds closures, lazy values and objects and inspects them with `Obj` on `ocamlopt` and `ocamlc`, for 500 rounds on each switch. A planted bug that reversed the closure environment gave 16 mismatches in 8 of 30 rounds, and one that dropped the object environment slot gave 8 mismatches in 4 of 30 rounds. It also caught two wrong object rules during development. The first version missed that methods read class parameters through instance-variable reads, so a used parameter looked unused. It also assumed that inheritance alone forces the environment slot.

## Stage 5 results

Every block shape now carries a *cost*, the words of memory that one value takes, counted as `Obj.reachable_words` counts them. A cost includes every header word. Block sizes elsewhere in the tool leave the header out, matching `Obj.size`. Text output adds a `cost:` line under each block, such as `cost: 3 or 5 words per node, with headers`, and a `not counted:` line that names the fields whose contents have no fixed size. JSON output gives each field an `owns` cost and each shape a `cost`. The rules are in `src/core/cost.ml`, and the model types `cost` and `shape_cost` are in `src/model/model.ml`.

**Rules.** A value's cost is its own block, size plus 1, plus the blocks that its fields own and whose sizes the types fix. A boxed float costs 2 words. An `int32`, `int64` or `nativeint` is a *custom block* of 3 words (header, operations pointer and one data word). A tuple costs its own block plus the costs of its elements. A `Some` block costs 2 words plus its argument, and a polymorphic variant with an argument costs 3 words plus the argument. Immediates cost 0. When a field's type is a variant, the cost lists every possible count, such as 3 or 5 words, up to 8 counts, and gives a range beyond that. The count stops at contents of no fixed size and names them as not counted. These are strings, bytes, arrays, closures, lazy values, exceptions, objects, abstract types and type variables. For OxCaml mixed blocks the cost is for native code, where flat fields take no block of their own, and bytecode boxes them. A mixed type reached through another type's field is not counted.

**Recursion.** A field whose type belongs to the same *recursive group* (`type ... and ...`) as the declaration is a further *node*. It is counted on its own, so the cost is per node. When any case of a declaration holds further nodes, every case says "per node", leaves included. An *abbreviation* in the group whose expansion is a type constructor, such as `u = t option`, is expanded, so its `Some` block counts. An abbreviation whose expansion is a polymorphic variant or a tuple is the node itself. Another recursive type, such as `float list`, is not counted in the cost. The tool gives it its own words per node instead, as `float list: 5 words per node`. The tool reads whether a type is recursive from the declarations, by checking whether its declaration reaches itself. Measured with `Obj.reachable_words` on values of 1,000 nodes, a record linked through `node option` takes 5 words per node. The same list as `Nil | Cons of { v : int; mutable next : t }` takes 3. A tree `Leaf | Node of tree * 'a * tree` takes 4, because `Leaf` is an immediate. An `int list` takes 3 words per element and a `float list` takes 5. `test/cases/recursive.ml` covers these types and their interactions with `[@@unboxed]`, polymorphic variants and mutual recursion.

**Oracle.** The fuzz oracle compares each predicted cost with `Obj.reachable_words` on the running program. It checks both backends, and checks mixed blocks on native code only. Native code shares equal *structured constants*, so `(Some 1, Some 1)` counts 5 words instead of 7. The checker therefore first copies each value with `Marshal` and the `No_sharing` flag. OxCaml cannot marshal mixed blocks, so the checker copies each value field of a mixed block as it builds the value. The empty array is one shared *atom*, which `Obj.reachable_words` counts once in a value but again in each node subtracted from it, so the generator for recursive types leaves it out. It subtracts further nodes and the shared extension slot of an exception. A cost with uncounted contents is checked as a lower bound. A field that holds a list sample with a known number of nodes is checked against the words per node. A new generator writes lists with tuple or inline-record cells, records linked through an option, binary trees and pairs of mutually recursive types. A planted bug that made a boxed float 3 words gave 94 mismatches in 20 rounds. One that dropped the header from blocks reached through another type gave 10 mismatches in 20 rounds. The oracle caught one wrong rule during development. An unboxed product such as `#(int16# * float array)` was taken for flat data, so its value parts went uncounted. A run of 300 programs from seed 1000 on OCaml 5.5 made 6,515 cost checks among about 29,000 checks per backend, with 0 failures. A run of 200 programs from the same seed on OxCaml made 5,045 cost checks among about 23,900, also with 0 failures.

## Oracle coverage

The fuzz checker used to walk the tool's predictions and check each one. A generated value that the tool failed to predict never appeared in that walk, so it was skipped and the run still passed. The checker now records each type and case that it checks, and reports a "no prediction" failure for every generated value that met no prediction. A package type without a prediction fails the same way. A missing backend fails with "no backend predicted", and a backend without closures with "closures not predicted". OxCaml native code is the one exception, because the tool does not predict flambda 2 closures by design. A planted bug that hid every third predicted declaration from the checker gave 74 "no prediction" failures in 10 rounds.

**Generators.** The generators now write type parameters, hidden, immediate and private types, objects, open rows, package fields and more forms of recursion. They build more closures, objects and lazy values. Generated modules hold functors, classes, extension constructors and function values, which are plain, partially applied, given an optional argument, or a recursive pair. Some package types carry `with type` constraints on abstract types, and some list every item in the module's order, so that packing copies nothing. Some packages are unpacked and packed again. On OxCaml the generators also write unboxed records, recursive mixed blocks and `vec128` fields.

**Differential checks.** Two *differential checks* compare the tool with itself instead of with a running program. Each fuzz round compiles the plain program with `ocamlc -bin-annot -stop-after typing`, reads the `.cmt` back for the active compiler, and compares the JSON of that model with the model read from the source. Only the file names of the unit and its labels may differ, and any other difference fails the round with a diff. The check takes about 60 ms a program, against about 2.8 s for a round of the oracle, and `-no-cmt` turns it off. The second check is `scripts/jsdiff.sh`. It builds the command-line tool, the fuzz executable and `web/jsoo/lense_web.bc.js`, then runs `scripts/jsdiff.cjs`. That node driver loads the bundle as the page's worker does and calls `lense_analyze` on each input. Its JSON and text must equal the output of `lense-ocaml --json` and plain `lense-ocaml`, with values shown, for the native, bytecode and both backends. The inputs are `test/cases`, `test/ox` and the programs that `fuzz.exe -gen DIR` writes, for both compilers. All inputs of one compiler run in one node process, as the page analyses every edit in one process, so state left over from one input shows up in the next. `scripts/jsdiff.sh 500` takes about 1 min 50 s once the bundle is built. Over 1,500 programs from seeds 1 and 5000 it compared 6,076 runs with no differences, after the type printer fix below.

**Planted bugs.** The planted bugs in the stage results above were each run by hand once, so nothing showed when a later change to a generator stopped catching one. `scripts/mutate.sh` repeats them. It copies the working tree, applies one *mutant* at a time to `src/core`, rebuilds, and runs the oracle on OCaml 5.5 and, with `-ox`, on OxCaml. The script fails when the oracle misses a mutant, and when a mutant no longer applies or compiles. The eight mutants make a boxed float 3 words, drop the header of a polymorphic variant block, give a one-constructor variant tag 1, and make constant constructors pointers. They also reverse constructor fields, reverse a closure environment, drop the object environment slot, and take a constant lazy value as suspended. Before the type-parameter generator landed, the two mutants on variant words survived. A run of 20 rounds from seed 1 on both compilers takes about 11 minutes. `dune test` always runs the same 20 programs from seed 1. The `@test/fuzz/fuzz` alias runs 100 programs from a new seed each time, and its `(universe)` dependency stops dune caching the result.

**Bugs found.** Six commits fixed wrong output, and a seventh made a vague prediction exact. Three came from the extended oracle. A field of function type was predicted as a `Closure_tag` block, but the second function of a recursive pair is an `Infix_tag` pointer. That gave 16 mismatches in 60 rounds from seed 1000, all in first-class modules. The object environment slot ignored `initializer` clauses and counted `self` as a variable of the enclosing item. That gave 6 mismatches in 3 of 100 rounds from seed 1000, and 0 after the fix. Inside a mixed block, a single-field unboxed record made its string slot look flat, so `{ m : #{ sa : #(float# * string) } }` got an exact cost of 4 words where the running program takes 6. Seed 1070 found it, in 100 OxCaml rounds from seed 1000. The seventh fix concerns OxCaml, where `[@@immediate64]` abstract types showed as "immediate or pointer". That prediction was vague, so the oracle never failed on it. With the fix, 100 programs from seed 1000 on OxCaml made 11 more immediate checks.

The other three came from the differential checks. With `--values`, a `.cmt` gave "not predicted" for its closures and two "Fatal error: Cannot find address for: x" lines, because the Lambda translation looked names up in environment summaries. The source digest check compared MD5 digests, but OCaml 5.3 and later record BLAKE128, so on 5.5 every `.cmt` was read without its source. Types then printed in the compiler's order, ``[ `On | `Off ]`` as ``[ `Off | `On ]``, and every lazy value was quoted as "lazy". On OxCaml the type printer kept its names from one unit to the next. After a file that translates a class for bytecode, a type `rr7` in the next file printed as `rr7/2`. `scripts/jsdiff.sh` found it over 500 fuzz programs in one node process, where 1 of 1,020 OxCaml runs differed.

**Final runs.** On the combined branch, a run of 200 programs from seed 9001 on OCaml 5.5 made about 19,315 checks per backend, with 0 failures. A run of 100 programs from seed 9001 on OxCaml made about 11,868, also with 0 failures. `scripts/jsdiff.sh 100 9001` compared 218 runs on 5.5 and 220 on OxCaml, with 0 differences. `scripts/mutate.sh -rounds 20 -seed 1 -ox` ran every mutant on both compilers. All 8 were caught.

**Limits.** Partial applications have no predicted block, so the oracle does not check them. After a GC, a forced lazy value can be its result instead of a `Forward_tag` block, so that check accepts either. `vec128` values are checked on native code only. The oracle cannot check `Any` words.

## Plan

**Stage 0.** Done. Every rule in this note was checked against the pinned OCaml release, with the results above.

**Stage 1.** Done. Variants, records, polymorphic variants and `[@@unboxed]`, read from typed `compiler-libs` output, with the `Obj` fuzz oracle from the start.

**Stage 2.** Done, and later removed. It showed module structures, signature coercions and the coercion of a unit to its `.mli`, but a named module is one block per program. Only first-class modules remain, checked by `test/packages.t` and the fuzz oracle.

**Stage 3.** Done. OxCaml mixed blocks and the byte map, built against OxCaml's own `compiler-libs` through `src/core/compat_ox.ml`. The fuzz oracle checks native code through `Obj.raw_field` and bytecode through the boxed values.

**Stage 4.** Done. Closures, lazy values and objects, in source order with the types, and one entry per closure for both backends. The fuzz oracle builds each value and checks it with `Obj` on both backends.

**Stage 5.** Done. The memory cost of each value, with headers, counted per node for recursive types. The fuzz oracle checks each cost against `Obj.reachable_words` on both backends.

Two pieces sit outside the stages. The `js_of_ocaml` web front end is done: a page in `web/` type-checks the source in the browser and shows the same report as the command line. Closure layouts under flambda are not predicted, for classic flambda on OCaml 5.5 and for flambda 2 in OxCaml native code, and the tool prints "not predicted" for them.

The C++ tool is mostly about the compiler's freedom to place fields. The OCaml tool is mostly about the compiler's freedom to choose a representation, and that choice is where OCaml programmers usually have the least visibility.
